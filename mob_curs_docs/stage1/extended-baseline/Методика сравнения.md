# Правила сравнения исходной и новой архитектуры

Этот комплект дополняет исходные метрики первого этапа. Измерительные копии не заменяют приложение в основном репозитории. Изменения стенда, дополнительные тесты и контрольные изменения хранятся отдельно от production-кода.

## Единицы измерения

| Вопрос | Что измерять | Что нельзя подменять этим результатом |
|---|---|---|
| Повторы отправки | Число серверных и локальных записей одной операции после заданного отказа | Отсутствие дублей во всех возможных сетевых ситуациях |
| Изоляция пользователей | Число чужих строк, возвращённых рабочим способом чтения истории на двухпользовательском fixture | Полноценный аудит авторизации реального backend |
| Покрытие | Covered / total для LINE и BRANCH на явно указанном наборе production-классов | Долю корректного поведения или только процент успешных тестов |
| Стабильность тестов | Таблица исходов одного теста при одинаковой подготовке на нескольких повторах | Утверждение о flakiness только по наличию падений |
| История | Отдельно время чтения БД и появления ожидаемого содержимого на экране | Время отрисовки всех 1000 карточек: LazyColumn рисует видимую область |
| Запуск | Отдельно Activity start и готовность проверяемого экрана | Сетевое время или производительность release по debug-сборке |
| Кадры | Число кадров и задержек при фиксированном жесте после подготовки данных | Производительность всех устройств |
| Память | Несколько точек при фиксированном числе переходов и одном процессе | Доказанную утечку только по росту PSS |
| Стоимость изменения | Фактически изменённые файлы, строки, затронутые роли и результат компиляции | Субъективную сложность или длительность работы другого разработчика |

## Подготовка сравнения на следующем этапе

1. Зафиксировать коммит и контрольные суммы production-исходников.
2. Сохранить неизменённые fixture, сценарии отказов, размеры базы и порядок действий.
3. Использовать те же устройство/API, вариант сборки и версию инструментов либо явно отметить отличие.
4. Разделять тесты исходного проекта и дополнительные исследовательские тесты. Падающий тест может дать покрытие выполненных строк, но не подтверждает их корректность.
5. Не исправлять дефект в исходной копии ради зелёной проверки. Тест может успешно подтвердить, что исходная версия создаёт дубль: это не означает корректность самого приложения.
6. Повторять измерения с одинаковой подготовкой БД/сессии и указать, включены ли загрузка данных и подготовка fixture во время.
7. Публиковать числители/знаменатели, а не только округлённые проценты.
8. Обезличивать пути, имена компьютеров и необязательные данные устройств до включения в Git.

## Ограничения интерпретации

Один повторяемый дефект достаточно подтверждает наличие проблемы в заданном сценарии. Отсутствие дефекта в конечном числе запусков не доказывает отсутствие всех гонок и отказов. На первом этапе фиксируется исходное поведение, а не проводится сертификация безопасности или промышленная нагрузочная аттестация.

Каждый эксперимент должен сохранять границу таймера, число повторов, исходные значения, подмены и результат. Эти сведения необходимы для ADR: решение обосновывается конкретной проблемой и проверяется тем же сценарием после реализации.
